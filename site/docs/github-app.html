The GitHub App

One app does sign-in, repository access and the agents' identity.

Early development. The registration flow below is built and tested against GitHub's documented API. It has not been exercised against a live GitHub account yet.

Registration by manifest

Instead of filling in a long form, the web service offers a GitHub App manifest flow on its first page while no App is configured. You press one button, GitHub shows the app's proposed name and settings, you confirm, and GitHub returns the app id, client id, client secret, webhook secret and private key for you to place in .env.

Repository permissions

PermissionAccess
ContentsRead and write
Pull requestsRead and write
IssuesRead and write
ChecksRead
ActionsRead (so the agents can read why a CI job failed)
MetadataRead
Organization: MembersRead (optional: lets a private member of an organisation listed in shelf.toml sign in; without it only public members can)

Workflows is optional, and off by default. GitHub refuses any push that changes .github/workflows unless the App has it. Granting it lets agents edit CI files, and a changed workflow runs with the repository’s secrets, so turn it on if you want that and keep GitHub’s safeguards on: a CODEOWNERS line for .github/ with code-owner review required, environments with required reviewers for deploy secrets, and approval for workflows from forks. They apply to the agents’ changes as to anyone’s. Under Permissions & events set Workflows to Read and write, then accept the change on each installation. The admin page shows whether it is granted. Without it, a step that must change a workflow fails with this explanation.

Webhook events

  • pull_request
  • issue_comment

Tick exactly these two in Permissions & events → Subscribe to events. A box is greyed until its permission is granted (Pull requests for the first, Issues for the second). pull_request tells Shelf a pull request was closed or merged; issue_comment carries /shelf commands and replies. Nothing else is read, so subscribing to more only adds noise.

GitHub also always sends installation, installation_repositories and ping events: they cannot be selected and need nothing from you. Webhooks are used in server mode. In local mode the app is polled instead.

Granting repositories

Install the app on your account or organisation and choose which repositories it may touch. Only repositories you grant appear in the picker, and the app can never reach the others.

Creating it by hand

The one-click registration fills all of this in for you. If you prefer the form on GitHub (Settings, Developer settings, GitHub Apps, New GitHub App), use these values, with your own address in place of https://shelf.example.org:

FieldValue
Homepage URLhttps://shelf.example.org
Callback URLhttps://shelf.example.org/auth/callback: where GitHub sends people back after they sign in.
Request user authorization during installationLeave unchecked.
Setup URL (optional)https://shelf.example.org/setup/installed: where people land after installing the App. Tick "Redirect on update".
Webhook: ActiveChecked.
Webhook URLhttps://shelf.example.org/api/github/webhook
Webhook secretA long random string that you make up, for example openssl rand -hex 32. Put the same value in GITHUB_WEBHOOK_SECRET. GitHub uses it to sign every delivery and the instance refuses any delivery that is not signed with it.
DescriptionWhat people read when they install or authorize the App. The registration page offers a ready text to copy (Markdown), and the one-click registration fills it in.
Where can this App be installed?Any account. With “Only on this account” GitHub answers 404 to everyone but you when they sign in. Public does not open your instance: who may use it is the list in shelf.toml.

Then set the repository permissions and events listed above. After creating the App, generate a client secret and a private key on its page and fill GITHUB_APP_ID, GITHUB_APP_SLUG (the name in the App's URL), GITHUB_APP_CLIENT_ID, GITHUB_APP_CLIENT_SECRET and GITHUB_WEBHOOK_SECRET in deploy/.env, and put the key file at deploy/secrets/github-app.pem.

Where each value comes from

All of these live on the App's settings page (Settings, Developer settings, GitHub Apps, Edit). Put them in deploy/.env:

VariableWhere it comes from
GITHUB_APP_IDTop of the page: App ID, a number.
GITHUB_APP_CLIENT_IDJust under it: Client ID, starting with Iv. It is not the App ID.
GITHUB_APP_SLUGThe name in the App's public link, github.com/apps/slug: the App name in lowercase with hyphens.
GITHUB_APP_CLIENT_SECRETUnder Client secrets, click Generate a new client secret. Shown once.
GITHUB_WEBHOOK_SECRETThe string you typed in the Webhook secret field (a long random string you make up). Exactly the same value.
the private keyUnder Private keys, click Generate a private key: your browser downloads a .pem file, once. It is not a line in .env: copy the file itself to deploy/secrets/github-app.pem on the server, for example scp ~/Downloads/*.pem you@server:~/shelf-sdlc-agents/deploy/secrets/github-app.pem. It is mounted read-only into the containers. On most servers chmod 600 is enough; if the service cannot read it, use chmod 644.

Two credentials, two jobs. The client secret lets people sign in. The private key is the App's own identity: it lets the agents clone, push and open pull requests. You need both. If one is missing, the service's log names it and says where to find it: docker compose -f deploy/compose.yml logs web.

If something goes wrong

  • Another person gets a 404 on github.com/login/oauth/authorize. The App is private, so GitHub hides it from every account but its owner. On the App’s page open Advanced, scroll to the bottom and choose Make public. They are still refused after signing in unless shelf.toml lists them.
  • "You must generate a private key in order to install your GitHub App." Normal after the manual form. Generate the key, then install.
  • The key was not downloaded. Generate another one on the same page. You can have several, and delete the lost one.
  • Sign-in loops or says the callback is wrong. The Callback URL must be exactly PUBLIC_URL plus /auth/callback, with no trailing slash and the same https.
  • Webhooks are refused. The webhook secret in deploy/.env differs from the one on GitHub. Look at the App's Advanced tab, Recent deliveries, for the response.
  • You see "App ID" where "Client ID" is wanted. They are two different values: the Client ID starts with Iv.
