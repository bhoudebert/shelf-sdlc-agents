Getting started

Self-host shelf-sdlc with one Docker Compose file.

Early development. The stack below boots and is tested on real Docker. A full run with a real model on a real repository is the next checkpoint, so expect rough edges and tell us about them.

What you will run

The compose file starts three services: Temporal (durable workflows, with its data on a volume), web (sign-in, the interface, webhooks; port 8080) and worker (runs the workflows and the agents; scale it with --scale worker=3). There is no bundled reverse proxy. Terminate TLS with a proxy you already have, a tunnel, or a Kubernetes ingress, and point it at the web service. Kubernetes manifests are not provided: deploy/compose.yml lists every service, variable and volume, which is all you need to translate it.

You need

  • A server with Docker and Docker Compose v2.
  • A public HTTPS address for the instance (GitHub redirects people and sends webhooks to it).
  • A model credential: an Anthropic API key, a Claude subscription token (claude setup-token), or an Anthropic-compatible gateway.

Steps

  1. Install. 
    git clone https://github.com/bhoudebert/shelf-sdlc-agents
cd shelf-sdlc-agents
sh deploy/install.sh https://shelf.example.org
    This writes deploy/.env with a generated session secret and starts the stack. Add your model credential to the file.
  2. Say who may sign in. The script created deploy/shelf.toml from shelf.toml.example; it is yours and git ignores it, so updates never touch it. Edit it (see Configuration). Leave both lists empty and anyone with a GitHub account can use, and spend, your instance.
  3. Register the GitHub App. Open your address. While no App is configured, the first page offers one click to register it with the right permissions and events, then shows the credentials once. Paste them into deploy/.env. See The GitHub App.
  4. Run the script again so the stack restarts with the App: sh deploy/install.sh.
  5. Install the App on the repositories you want to use (the board links to it), and sign in.

Environment variables

deploy/.env.example documents every variable. The ones you set:

VariablePurpose
PUBLIC_URLThe public address of the instance, with no trailing slash. Used for sign-in callbacks and webhooks.
SESSION_SECRETRandom secret that signs the session cookies. install.sh generates one.
WEB_PORTThe host port the web service is published on (default 8080).
GITHUB_APP_ID, GITHUB_APP_SLUG, GITHUB_APP_CLIENT_ID, GITHUB_APP_CLIENT_SECRET, GITHUB_WEBHOOK_SECRETThe App's credentials, shown once after the one-click registration. Empty on the first start.
the private key fileNot an environment variable: put the .pem you downloaded at deploy/secrets/github-app.pem. It is mounted read-only into the containers.
CLAUDE_CODE_OAUTH_TOKEN, ANTHROPIC_API_KEY, or ANTHROPIC_BASE_URLHow the agents get a model. Set one. The agents run inside the worker container, so the claude login on your server is not visible to them: run claude setup-token and put the token in deploy/.env, or use an API key. Without one, steps fail with “Not logged in”.
SHELF_MODEL, SHELF_MAX_TURNS, SHELF_MAX_BUDGET_USDOptional: force a model, and bound what one step may use.
TEMPORAL_ADDRESS, TEMPORAL_NAMESPACEUse your own Temporal instead of the bundled one (and delete that service).

Local or server mode

Set mode in deploy/shelf.toml. In server mode GitHub's webhooks wake waiting work, and a slow poll is a safety net. In local mode there is no public address, so waiting work looks at GitHub on a durable timer that slows down while nothing happens.

After it is running

  • Logs: docker compose -f deploy/compose.yml logs -f.
  • Look inside Temporal. Sign in as an administrator and open /temporal on your address (for example https://shelf.example.org/temporal), or follow “Inspect in Temporal” on any work page. You can list workflows, read each one's history and run queries. It is read-only by default; set TEMPORAL_UI_WRITABLE=1 in deploy/.env to also allow signals and termination. Temporal's own port is never published: its interface has no login, so it is reachable only through this protected path. For the command line: docker compose -f deploy/compose.yml exec temporal temporal workflow list.
  • Check that the agents work. Run docker compose -f deploy/compose.yml exec worker shelf-doctor: it asks real, tiny agent tasks in a throwaway repository (a shell, the repository's CLAUDE.md, the pull request title convention, running commands in the sandbox, the credential) and tells you what to do about each failure. Agents run in the worker container with the credential from deploy/.env, not with your own login on the server. If it reports that the sandbox cannot start (Ubuntu 23.10 and later restrict the user namespaces it needs), run sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0 on the server, persist it in /etc/sysctl.d/, restart the worker and run the doctor again. Turning the sandbox off (SHELF_SANDBOX_DISABLED=1) is a last resort for repositories you fully trust: without it an agent can read the worker's environment and secrets.
  • Tools for the agents (a JDK, Maven, Node…). The worker image carries none. If a repository declares what it needs in mise.toml or .tool-versions, the agent runs mise install and then the repository’s own build and tests, as a developer would. Downloads and package caches live in a volume, one home per repository, so nothing one repository downloads is used by another. The sandbox may reach GitHub, the tool downloads and the common registries; add a private mirror with SHELF_ALLOWED_DOMAINS in deploy/.env. A repository with no declaration gets no tools: the agent says so instead of pretending it ran the tests.
  • The checks rely on your CI. After the repository’s own commands (checks in its config) pass, the checks read the pull request’s CI as the App. A run that failed, timed out or was cancelled sends the work back to the implementer with what it reported. A run still going makes the work wait: one step looks every minute for half an hour (SHELF_CI_WAIT), then looks again later without losing a round. A commit with no CI run within two minutes (SHELF_CI_GRACE) counts as a repository without CI. The code reviewer is told what the CI says and cannot approve over a red or unfinished one. Older CI systems that report commit statuses are read too when the App is allowed to see them.
  • Agents cannot run commands (Ubuntu 23.10+). If the doctor says the sandbox cannot start, run sh deploy/fix-ubuntu.sh on the host. It shows what Ubuntu restricts (a kernel setting and an AppArmor profile for bwrap), says what it will change and what that costs, asks, applies both, restarts the worker and runs the doctor again. --undo puts Ubuntu’s defaults back. Do it on a host dedicated to this stack. install.sh tells you when it is needed.
  • Check the GitHub App. The admin page asks GitHub, as the App, which events it subscribes to, its permissions, its webhook URL and secret and its latest webhook deliveries, and tells you what to change (for example tick Pull request and Issue comment under Permissions & events). Reload it after a change.
  • Administrators (listed in shelf.toml) see the work of every repository on the board and may decide at any gate. Everyone else sees only what is on repositories they can open.
  • Update: git pull and run the install script again.
