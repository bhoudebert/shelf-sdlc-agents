Concepts

The few ideas everything else is built from.

The pipeline

Work moves through ten phases. Each has a kind: an agent produces a document or the code, an agent on another model reviews it, the repository's own commands verify it, a person decides at a gate, and at the end a person merges.

PhaseKindWhat happens
SpecproduceAn agent (intake) writes spec.md from your request.
Spec reviewreviewA reviewer (spec_critic) on another model asks for changes or approves. The loop goes back to the spec.
Spec approvalgateA person approves. This stop is on by default and can be turned off per run.
Designproducearchitect writes design.md.
Design reviewreviewdesign_reviewer judges it. On by default, optional.
Planproduceplanner writes plan.md.
Implementationproduceimplementer writes the code in a fresh clone; the worker commits and pushes.
ChecksverifyThe repository's own commands run, then its CI is read. Red goes back to the implementer.
Code reviewreviewcode_reviewer reads the change and cannot approve over a red or unfinished CI.
Pull requestmergeThe pull request is ready for people. A person has the last word: the merge.

On the board and the work page these ten phases are the timeline you see. Each shows done, in progress, waiting, stopped or not yet, with a glyph and a word, never colour alone.

Entry points

Work does not have to start at the beginning. The start form offers seven ways in, and each skips the phases already done elsewhere.

You start withIt runs
A needEverything, from the spec.
A specSpec review, your approval, then the rest.
A design to makeFrom the design (the spec is approved).
A plan to makeFrom the plan (the design is done).
Code to writeFrom the implementation, then checks, code review, the pull request.
Review my pull requestCode review only, read only: nothing is changed on the pull request.
Work on my pull requestThe agents change its branch as you ask, wait for its CI and review the result.

A repository may offer fewer entry points: the entries key of its .shelf/config.toml.

Gates and decisions

At a gate the work stops and waits for a person. The decisions are a closed list: approve, request changes (with a note the agents receive), resume (after a failure), reject and abort. They come from the web page or from a /shelf comment on the pull request. A model never interprets them, so text written by or into a model cannot approve its own work.

Loops and rounds

When a reviewer asks for changes, or checks fail, the producer tries again. Each attempt is a round, and every loop has a maximum (max_rounds, 3 by default in the example config). When it is reached the work escalates to a person instead of continuing. A reviewer is a different model from the producer, so a review is not the same model agreeing with itself. This makes a run slower than asking one agent; Limits says why and what is planned.

Roles and access

There is no user database. The operator's shelf.toml lists the organisations and users allowed in, and the administrators; access is closed by default. Each repository can then grant per-repository roles in .shelf/config.toml. See Roles and stops.

Durable work

Each work item is a Temporal workflow. It keeps its place across restarts and deploys, and waiting for a person costs nothing. The workflow decides nothing itself: it feeds events to one pure function, decide(course, state, event), and runs the commands it returns.

The guard

Every agent runs under Warden, which judges each command, file access and fetch before it runs. The guard shows it deciding.

Where a run's files go

A run writes its own documents to .shelf/<work-id>/ on the work's branch (request.md, spec.md, design.md, plan.md), and the work page shows them.

What lasts goes where the repository keeps it: requirements in its specs folder (openspec/specs/ by default) and decision records in its decisions folder (docs/adr/), created when missing. A new record is checked against the earlier ones. Set the folders and the strictness in .shelf/config.toml. Older runs left their files in docs/shelf/, which is still read.
