Configuration reference

Two files and a catalog: one for the operator, one for each repository.

shelf.toml (operator)

Kept by whoever runs the instance and mounted into the container. It decides who may sign in, and how waiting work learns what happened on GitHub. An empty file is a closed instance in local mode: nobody can sign in until it names someone. Unknown keys are refused, so a typo is an error, not silence.

# shelf.toml
mode = "server"            # "local": no public address, poll GitHub often
                           # "server": webhooks wake the work, the poll is a slow safety net

[access]
orgs   = ["acme"]          # members of these organisations may sign in
users  = ["alice", "bob"]  # these users may sign in
admins = ["alice"]         # may sign in, and may decide at any gate

Access is closed by default. A person signs in only if they are in users or admins, or belong to an organisation in orgs; everyone else is refused. With all three empty nobody can sign in, you included, so name yourself first. The same list governs /shelf commands written on a pull request: someone outside it is ignored, whatever their rights on the repository.

Repositories follow the same list. Anyone can install the GitHub App on an account or organisation of their own, so being able to reach a repository proves nothing. Shell only shows, starts work on and obeys /shelf commands for repositories owned by a listed organisation, a listed user or administrator, or the signed-in person themself. Repositories of any other owner are ignored, even where the App is installed.

Skills and plugins for agents (catalog.toml)

Agents already read what a repository tells them (CLAUDE.md, AGENTS.md, its skills and rules). The operator can give every agent more, such as test-driven-development or GDPR skills, in deploy/config/catalog.toml. Each source is a git repository pinned to a full commit, never a branch or a tag, so a change is a change you review. sh deploy/install.sh fetches them. Nothing a source contains is run while it is fetched, and a failed fetch keeps the previous catalog.

# deploy/config/catalog.toml
[[source]]
name   = "superpowers"
git    = "https://github.com/obra/superpowers"
ref    = "22f0b463e7a5e579904dd6211a520321035526f7"   # a full commit
kind   = "skills"
skills = ["test-driven-development", "systematic-debugging"]

[[source]]
name = "gdpr"
git  = "https://github.com/github/awesome-copilot"
ref  = "8ecd5b17f02fe5fbebf35eccd1867265eded811f"
kind = "skills"
path = "skills/gdpr-compliant"                    # one folder of a larger repository

There are two kinds. skills takes only the skill folders, as a plugin without hooks, and loads them for the roles you bind it to in shelf.toml. plugin takes the whole plugin, hooks included, and enables it for every agent through a managed policy that also stops a repository's own hooks. A plugin's hooks run commands, so the sync lists them in catalog.lock.json for you to review, and the image ships node for the ones that need it.

A [[hook]] entry runs a command of your own for every agent, for example rtk hook claude before each shell command (the image carries rtk, the open-source edition): event, optional matcher and command. It is written by you and never fetched.

# shelf.toml
[roles.implementer]
use = ["superpowers"]

[roles.code_reviewer]
use = ["superpowers", "gdpr"]

The roles are intake, spec_critic, architect, design_reviewer, planner, implementer, code_reviewer and titler. An edit of the bindings applies without a restart. A name the catalog does not have is skipped with a warning in the worker's log.

Every agent also starts with telemetry and Claude Code's automatic memory off, so nothing one step learns is carried into another.

Warden: the guard around every agent

Every agent runs under Warden, which the image builds from the same commit. It is called before each command, file access and fetch, through the managed policy that shelf-catalog sync writes (so a repository’s own settings cannot remove it). It denies what the profile denies, runs allowed commands through a redactor (secrets and personal data become tokens such as <EMAIL_1>, restored when an agent writes them into a file) and logs every decision. If Warden itself fails, the call is refused.

# deploy/.env
SHELF_WARDEN_PROFILE=shelf     # shelf (default), strict, or observe: log only, block nothing
SHELF_WARDEN=on                # off: no guard (then run install.sh again)

deploy/config/warden.toml (created from warden.toml.example, every line commented) is your policy. It is loaded as a locked layer: a repository can add rules and protect more files in its own .warden/policy.toml, and can never loosen yours.

[[rules]]
id = "no-prod"
match = 'kubectl .*--context[= ]prod'
decision = "deny"
reason = "production is hands-off for agents"

[redact.pii]
names = ["Acme Corp"]
custom = [{ name = "customer_id", pattern = 'CUST-\d{6}' }]

To see it work, from deploy/: docker compose exec worker warden policy (what is in force), warden explain '<command>' (how one command is judged), warden status (what it refused and redacted) and warden audit verify (the log has not been changed). Start with observe for a week: it logs what it would have refused and refuses nothing. After that week, docker compose exec worker warden report says how many calls it would have stopped, per risk and per command: if the list is what you expected, switch to shelf. The same counts, and whether the log’s chain is intact, are in the Guard section of the admin page. What Warden is not, in Limits.

.shelf/config.toml (per repository)

Lives in the repository, so changes to who may do what are reviewed like any other change. Every key is optional.

# .shelf/config.toml
entries = ["need", "spec", "design", "plan", "implement", "pull_request_review", "pull_request_work"]
base_branch = "main"
checks = ["make test"]      # what the verify step runs

[policy]
max_rounds = 3             # how many times a loop may send work back before a person is asked
spec_approval = true       # a person approves the spec before the design starts
design_review = true       # a reviewer checks the design before the plan
proceed_on_deadlock = false  # go on, with the open points posted, when a spec or design review cannot settle

[roles]                    # without roles, any signed-in person may decide
product_owner = ["alice"]  # decides at the spec gate
architect     = ["bob"]
tech_lead     = ["bob", "carol"]
developer     = ["dan"]

Roles limit who may decide only once you set them. The spec gate belongs to product_owner, the design review to architect and tech_lead, and the pull request to tech_lead and developer. Administrators may always decide.

The three [policy] choices about stops are only defaults. The start form shows them, preset from the repository, and what you leave checked there is what that work runs with, so a file edit never changes work already running. proceed_on_deadlock lets work go on past a spec or design review that cannot settle (it answers escalate, or the loop used its rounds): what stayed open is posted on the pull request and the agents write their assumptions down. The code review, the repository’s checks and the merge always stay: a red check or a code review that cannot decide still waits for you. Fewer stops mean more autonomy, less control and potentially less quality.
