Roles and stops

Who decides, where a run stops, and how much it may do without you.

Roles

With no [roles] in the repository, any signed-in person the instance allows may decide. Once you set roles, they limit who may decide:

GateWho may decide
The specproduct_owner
The design reviewarchitect, tech_lead
The pull requesttech_lead, developer

Administrators (the admins list of the operator's shelf.toml) may always decide. A decision from someone without the role is refused, in the web page and on the pull request alike.

Who gets in at all

There is no user database. A person signs in only if they are in users or admins of shelf.toml, or belong to an organisation in orgs. The same list governs /shelf commands on a pull request: someone outside it is ignored, whatever their rights on the repository. Shelf also shows and starts work only on repositories owned by a listed organisation, a listed user, an administrator, or the signed-in person themself, even where the App is installed on others.

The closed list of decisions

Approve, request changes (a note is required, because it is what the agents receive), resume, reject, abort. Matched by word, never interpreted by a model.

Where a run stops

  • The spec gate. A person approves before the design starts.
  • A review that cannot settle. The writer and the reviewer disagree for good, or the loop used its rounds: a person is asked.
  • A failure. A step that still fails after its retries becomes a wait for a person, who can resume.
  • The merge. Always a person.

Let a run go on overnight

The start form has three boxes under "How much may this run do without you?", preset from the repository's [policy]. Every box is worded so that checked means more control: leave them all checked and the run is fully attended.

BoxUnchecked means
Wait for my approval of the specThe design starts as soon as the spec reviewer is satisfied.
Have the design reviewedNo agent checks the design before the plan.
Stop and ask me when a spec or design review cannot settleThe work goes on. What stayed open is posted on the pull request, and the agents write their assumptions down.

Fewer stops mean more autonomy, less control and potentially less quality. Nobody is asked at a stop you removed, so a spec or design can reach the pull request with open points or unchecked assumptions: read them on the pull request before you merge.

What always stays: the pull request is never merged without you; the code review and the repository's checks always run; a red check or a code review that cannot decide still waits for you.

The choice is recorded for that run, so a later edit of the file does not change work in flight. The board and the work page say which stops a run does without. The matching defaults are spec_approval, design_review and proceed_on_deadlock in [policy]; the reasons are in decision record 0013.
