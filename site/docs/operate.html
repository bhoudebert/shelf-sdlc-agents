Operate

Keeping an instance healthy, and finding out why a work failed.

Logs and Temporal

docker compose -f deploy/compose.yml logs -f

Sign in as an administrator and open /temporal on your address (or follow "Inspect in Temporal" on any work page) to list workflows, read each one's history and run queries. It is read-only unless you set TEMPORAL_UI_WRITABLE=1 in deploy/.env, which also allows signals and termination. Temporal's own port is never published: its interface has no login, so it is reachable only through this protected path. From the command line:

docker compose -f deploy/compose.yml exec temporal temporal workflow list

Check that the agents work

docker compose -f deploy/compose.yml exec worker shelf-doctor

It runs tiny real agent tasks in a throwaway repository and tells you what to do about each failure. Agents run in the worker container with the credential from deploy/.env, not your own login on the server.

Agents cannot run commands (Ubuntu 23.10 and later)

If the doctor says the sandbox cannot start, Ubuntu restricts the user namespaces it needs, in two places. On a host dedicated to this stack:

sh deploy/fix-ubuntu.sh

It shows what Ubuntu restricts, says what it will change and what that costs, asks, applies both, restarts the worker and runs the doctor again. --undo puts Ubuntu's defaults back. Turning the sandbox off (SHELF_SANDBOX_DISABLED=1) is a last resort for repositories you fully trust: without it an agent can read the worker's environment and secrets.

Debug a work that fails

The work's page shows the error. For the full picture:

docker compose -f deploy/compose.yml exec worker shelf-diagnose work-...      # or owner/repo#number for a pull request

It replays what a step meets, with the App's real credentials: which installation covers the repository and what it was granted, what GitHub says the pull request is, what git can list and fetch, and the latest failed attempts of the work with their times. No secret is printed, so the output is safe to paste into an issue. An administrator can also close a work that can no longer be steered, from its page.

The admin page

  • GitHub App check. Asks GitHub, as the App, which events it subscribes to, its permissions, its webhook URL and secret, and its latest deliveries, and says what to change. Reload after a change.
  • Guard. What Warden recorded, and whether the audit chain is intact (the guard).
  • What GitHub has sent. The latest webhook deliveries since the instance started; compare with the App's Recent deliveries on GitHub.
  • This instance. The facts of the deployment.

Keep spend in check

Bound one step with SHELF_MAX_TURNS and SHELF_MAX_BUDGET_USD, and force a model with SHELF_MODEL. The worker logs the cost of each step. Shelf also starts agents with telemetry and Claude Code's automatic memory off, so nothing one step learns is carried into another.

Clean the tools cache

Each repository's tools and package caches live in its own home in the worker-cache volume. They grow. Remove the homes nothing used for 30 days with docker compose -f deploy/compose.yml exec worker shelf-cache prune (add --older-than 7 for a different age, or --dry-run to see what would go). It says what it removed and how much space that freed; the tools are installed again, in seconds, the next time a repository needs them.

Nix, for repositories whose environment is a flake (optional)

Off by default. Set SHELF_NIX=on in deploy/.env and run sh deploy/install.sh again: it adds compose.nix.yml, a Nix daemon as a service of its own with a persistent store (a volume that outlives every update, or a folder of the host if you set SHELF_NIX_STORE=/var/lib/shelf-nix). The worker mounts the store read-only and builds through the daemon, so nothing the worker or an agent runs can write it.

Then, for the developer and the code reviewer, a repository gets its flake's development shell as the agents' environment when its CI runs through Nix (a workflow that installs Nix or runs nix develop), or when it declares no tools for mise and its CI sets up none the worker knows. A repository whose CI uses setup-node and the like keeps getting those versions, as before. The worker asks Nix for the shell's environment without entering it, so no lock file is written into the repository and its shell hook never runs; the agent gets the PATH of the shell and its plain variables. The first time costs seconds to minutes of downloading; after that the store has it.

What it costs, honestly. Evaluating a repository's flake runs Nix code from that repository in the worker, outside the agents' sandbox, in a scrubbed environment (no token, no credential) and as a user the daemon does not trust. The daemon builds without the Nix sandbox, because a container cannot give one, with network access and as root inside its own container, which holds no secret. Turn it on for repositories whose people you trust, as you would for their checks. The store grows: the daemon collects garbage by itself when the disk runs low, and docker compose -f deploy/compose.yml -f deploy/compose.nix.yml exec nix nix-collect-garbage -d empties it by hand (the next work downloads again).

Docker in steps (optional, needs a runtime on the host)

Some repositories cannot be built or tested without starting containers: a database, an OAuth2 server, a cache, a browser, a service built from their own Dockerfile, started with docker compose, with Testcontainers or with docker run. In container mode (SHELF_ISOLATION=container) a step can have a Docker daemon of its own, inside the step, in a small virtual machine of its own. What it starts lives and ends with the step, and nothing reaches the Docker of the host. The reasons are in decision 0020.

Status. Set SHELF_STEP_DOCKER=on and SHELF_STEP_RUNTIME=kata in deploy/.env (with SHELF_ISOLATION=container) and run sh deploy/install.sh: it checks the host with the script below and, with --install-runtime (or when you answer yes), installs what is missing. The developer and the code reviewer then have the daemon, and are told so; the other steps do not. Not yet proven on a real host: the script and the step have been tested against fakes, and the image builds, but nobody has yet seen a daemon run inside a Kata step. Images are pulled again by each step: there is no cache between steps yet.

What the host needs

RequirementWhy, and how to check
Ubuntu or Debian, on x86_64 or arm64The script installs a package set for these only. On anything else it stops before changing anything, and you install a runtime yourself and name it in SHELF_STEP_RUNTIME.
Docker Engine 26 or laterdocker version.
/dev/kvmThe runtime (Kata Containers) starts a virtual machine per step. ls -l /dev/kvm. On a cloud server, which is itself a virtual machine, the provider must allow nested virtualisation: systemd-detect-virt says kvm or similar, and /dev/kvm exists when it is on.
Kernel modules vhost_vsock and vhost_netThe script loads them and keeps them across reboots.
root, and about 1 GB of downloadThe script changes the system. Use sudo.

One script, safe to run again

sh deploy/host-runtime.sh --check      # changes nothing: which steps are done, which are missing
sudo sh deploy/host-runtime.sh         # does the missing ones, after listing them and asking
sudo sh deploy/host-runtime.sh --yes   # the same without asking (needed without a terminal)

Each step checks whether it is done and skips it if so. It does, in this order, and says before it starts what it will do:

  1. Checks the platform (above). If anything fails, nothing is changed and it says what and which other options exist.
  2. Loads the two kernel modules, and lists them in /etc/modules-load.d/shelf-kata.conf.
  3. Installs with apt what it needs and the host lacks (curl, zstd, jq).
  4. Downloads one pinned release of Kata Containers (4.4.0), checks its SHA-256 against the one in the script, unpacks it aside and moves it into /opt/kata only when whole. A download that does not match is never unpacked.
  5. Adds the runtime to /etc/docker/daemon.json, keeping what is already there and a dated copy of the file first. A file that is not valid JSON is left as it is.
  6. Asks Docker to reload its configuration and checks that the runtime is listed.
  7. Proves it: a container under the runtime reports a kernel other than the host's, and a Docker daemon inside one runs a container. That second proof is what a repository's checks use: a container with a healthcheck must become healthy, a command must be executed in a running container (a healthcheck is exactly that, so where it fails nothing can ever be healthy), and a port that your host already uses must answer from inside the step (the daemon publishes in the step's own network, so it cannot clash with your services or with another step). It tries the profiles below from the least permissive and says which one this host needs.

The profile: what this host lets a step do

A Docker daemon needs a writable cgroup filesystem and /proc/sys (it makes a cgroup for everything it starts and sets ip_forward), and a container gets both read-only. The step's own start makes them writable. Beyond that, what a host's guest kernel and filters allow differs, so the step is started with one of four profiles, each adding to the one before: standard (the capabilities a daemon needs and nothing else), unconfined (also without the guest's seccomp and AppArmor filters), systempaths (also without its read-only and masked system paths) and full (also all capabilities and the guest's cgroup namespace: everything privileged mode gives except the host's devices). None of them is privileged mode: under Kata, privileged mode hands the host's devices to the virtual machine, and on a real host it failed. You do not choose: sh deploy/install.sh asks sh deploy/host-runtime.sh --probe to try them in turn on this host, writes the first that works as SHELF_STEP_DOCKER_PROFILE in deploy/.env, and does not ask again. If none works, it says so, shows what each attempt printed, and Docker in steps cannot be used on this host.

The resolvers: a step must be given real ones

On a user-defined network Docker puts its own resolver (127.0.0.11) in a container's resolv.conf. That resolver lives in the host's network namespace, so a virtual machine cannot reach it, and a step with Docker could not resolve any name: the agent ended after minutes with API Error: Can't reach the API server (EAI_AGAIN). So the step is given the resolvers of your host: SHELF_STEP_DNS, addresses separated by commas, written into the step's /etc/resolv.conf before its daemon starts (the containers the daemon starts inherit it). You do not choose them: sh deploy/install.sh asks sh deploy/host-runtime.sh --probe to find your host's upstream resolvers (the ones Docker copies on its default network, without loopback ones such as 127.0.0.53) and to prove from inside a step, on a user-defined network, that a name resolves with them, then writes them into deploy/.env once. If your host has only a loopback resolver, or none a step can use, the probe says so and you set SHELF_STEP_DNS yourself to resolvers a virtual machine can reach.

What it does to the containers already on the host

A reload does not stop running containers: on Ubuntu 25.04 with Docker 28.2.2 and live restore off, a reload left all fifteen containers of one host running. Whether a changed runtimes entry is taken up by a reload is what the script checks. If Docker does not list the runtime afterwards, the script stops, lists the containers a restart would stop (when live restore is off, every running one), and restarts Docker only if you run it again with --restart-docker.

What it costs, honestly

  • A step that asks for a daemon pays for a virtual machine and a daemon starting. It has not been measured here yet; the install check will print the time the proof took on your host.
  • On a cloud server the virtual machine runs inside another one (nested virtualisation), which is slower than on bare metal.
  • The isolation is as strong as the runtime. A step can start any container it likes, inside its own boundary; what it can reach is decided by the same network rules as the step's.
  • This script installs Kata Containers only. Another runtime (gVisor, sysbox) is yours to install; set SHELF_STEP_RUNTIME to its name and run the script with --check to see whether Docker lists it. Sysbox has a reported failure on Ubuntu 25.04 with kernel 6.14 (issue 947).

Skills and plugins for agents

Pinned sources and role bindings live in deploy/config/catalog.toml and shelf.toml; sh deploy/install.sh fetches them. See Configuration.

Read another repository as reference

Write it in the request: "implement the CI like https://github.com/foo/bar". Up to three public repositories per work are read as plain, read-only archives in a folder git ignores. The work page says which ones it reads.

Update

git pull
sh deploy/install.sh

Work started before a protocol change keeps its old behaviour: restart the work to get the new flow. Updating from an older install needs the script once, which moves shelf.toml into deploy/config/.

Before you trust it with a repository

Read Limits before you point Shelf at a repository you care about: agents are not isolated from each other or from the worker, so run Shelf for repositories whose people you trust.
