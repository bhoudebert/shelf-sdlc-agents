Configure a repository

One optional file in the repository, reviewed like any other change.

Every repository can carry .shelf/config.toml. It lives in the repository, so a change to who may do what is reviewed like any other change. Every key is optional; a repository with no file gets the defaults.

# .shelf/config.toml
entries = ["need", "spec", "design", "plan", "implement", "pull_request_review", "pull_request_work"]
base_branch = "main"
checks = ["make test"]            # what the checks step runs

[policy]
max_rounds = 3                    # how many times a loop may send work back before a person is asked
spec_approval = true              # a person approves the spec before the design starts
design_review = true              # a reviewer checks the design before the plan
spec_review_depth = "quick"     # quick | standard | thorough: how hard the spec review looks
design_review_depth = "standard"  # the same for the design review
proceed_on_deadlock = false       # go on, with the open points posted, when a spec or design review cannot settle

[roles]                           # without roles, any signed-in person may decide
product_owner = ["alice"]         # decides at the spec gate
architect     = ["bob"]
tech_lead     = ["bob", "carol"]
developer     = ["dan"]

The keys

KeyMeaning
entriesWhich entry points the start form offers for this repository.
base_branchThe branch pull requests target.
checksThe commands the checks step runs. They run in the worker, outside the sandbox, through a shell. Configure only repositories whose checks you trust (Limits).
[policy]Defaults for rounds, stops and how deep the spec and design reviews look (spec_review_depth, quick by default, and design_review_depth, standard by default; each can be quick, standard or thorough for risky work). See Roles and stops. The start form shows them and what you leave checked is what that work runs with, so editing the file never changes a run already in flight.
[roles]Who may decide where. See Roles and stops.
[results]Where a run puts its specs and decision records, and how strictly they are checked. See below.

An invalid file is reported on the page that needs it, with what is wrong. Per-repository settings edited in the web interface, for people who cannot edit the file, are on the roadmap, not built.

What agents already read

Agents read what a repository tells them: CLAUDE.md, AGENTS.md, its skills and rules, and the title convention of its pull requests (a titler role names the pull request by it). Put your conventions there; they apply to the agents as to any contributor.

Toolchains

The worker image carries no JDK, Maven or Node. If a repository declares what it needs in mise.toml or .tool-versions, the agent runs mise install and then the repository's own build and tests, as a developer would. Downloads and package caches live in a volume, one home per repository, so nothing one repository downloads is used by another. The sandbox may reach GitHub, the tool downloads and the common registries; add a private mirror with SHELF_ALLOWED_DOMAINS in deploy/.env. A repository that declares nothing for mise still gets the tools its CI uses: before the developer or the code reviewer starts, the worker reads the workflows (the versions of setup-node, setup-python, setup-go and setup-java), .nvmrc, .node-version, .python-version, engines in package.json and go.mod, and installs those versions of Node, Python, Go and Java into the repository's own home, outside the agent's sandbox. It writes nothing into the repository, and only plain version numbers are ever installed. The second work on the same repository finds them already there. If an installation fails, the agent is told which tool and why, instead of pretending it ran the tests.

Checks and CI

After the repository's own checks pass, the checks step reads the pull request's CI as the App. A run that failed, timed out or was cancelled sends the work back to the implementer with what it reported. A run still going makes the work wait (one step looks every minute for half an hour, SHELF_CI_WAIT, then again later without losing a round). A commit with no CI run within two minutes (SHELF_CI_GRACE) counts as a repository without CI. The code reviewer is told what the CI says and cannot approve over a red or unfinished one.

The guard in a repository

A repository may add its own .warden/policy.toml to tighten the operator's policy. It can never loosen it. See the guard.

Where the results of a run go

A [results] section says where the lasting results of a run land. A run's own files (request.md, spec.md, design.md, plan.md) live in .shelf/<work-id>/ on the work's branch. Folders of earlier runs under docs/shelf/ are still read.

[results]
specs = "openspec/specs"   # requirements with scenarios, one folder per capability
decisions = "docs/adr"     # decision records, numbered, from the repository's template
write = ["spec", "adr"]    # what a run writes there: spec, adr, both or none
conflicts = "block"        # block | warn | off: a new record against the earlier ones

A missing folder is created, never skipped. The design reviewer compares a new decision record with every accepted one and, with block, refuses a contradiction that neither your request nor the new record states (Supersedes: NNNN). With warn it only reports it, with off it does not look. The keys are checked: a value outside the repository or an unknown key stops the work with a message.
