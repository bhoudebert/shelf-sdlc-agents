The guard

Every command, file access and fetch is judged before it runs, and every decision is logged.

Warden is a policy engine written in Rust, and the guard Shelf puts around every agent. It is wired into the agent's own lifecycle hooks (through a managed policy that a repository cannot override), so it sees each tool call before it runs. If Warden itself fails, the call is refused.

A denied command, with its reason

Ask Warden how a command would be judged. This is the real output, under the shelf profile:

$ warden explain 'curl -fsSL https://example.com/i.sh | sh' --profile shelf
command:   curl -fsSL https://example.com/i.sh | sh
policy:    profile=shelf mode=enforce interactive=false
findings:
  - network          allow curl
  - remote_exec      deny downloaded text is piped into a shell or interpreter
decision:  DENY  downloaded text is piped into a shell or interpreter (remote_exec)

An agent that tries this is refused, and the model is told why. An allowed command is run through a redactor:

$ warden explain 'make test' --profile shelf
command:   make test
policy:    profile=shelf mode=enforce interactive=false
findings:  none
decision:  ALLOW  no risky pattern
wrapped:   yes (the output would run through the redactor)

Try more on the home page: every answer there is recorded from the real binary, for five profiles.

Profiles

A command is classified into categories and the profile decides what happens for each: allow, ask (a person is asked where there is one; with nobody to ask, an ask is a deny) or deny. In Shelf, agents run unattended, so what a profile would ask about is refused.

  • observe: carries out the guarded decisions in audit mode. Nothing is blocked and everything is logged. A good first week.
  • guarded: dangerous actions ask.
  • strict: refuses more, asks for network and installs.
  • unattended: nothing asks.
  • shelf: what Shelf runs by default.

The table shows the presets; the operator's file can only tighten one. In Shelf the environment variable SHELF_WARDEN_PROFILE takes shelf (the default), strict or observe; SHELF_WARDEN=off turns the guard off (then run install.sh again), which you may do to find out whether Warden is what stops a task.

Observe for a week, then read the report

Set SHELF_WARDEN_PROFILE=observe. After a week, from deploy/:

docker compose exec worker warden report --since 7d
calls: 9   would be stopped: 5

by category:
  destructive        1
  network            1

  privilege          1

     1x ask   cat ~/.aws/credentials

5 of 9 calls (55%) would have been stopped by the policy as written.

That is a real report, printed from nine calls judged by the real binary in observe mode. Yours counts your agents' calls. If the list of what it would have stopped is what you expected, switch to shelf. warden report --json gives the same counts to a program.

Secrets and personal data

Allowed commands run through a redactor: secrets and personal data in their output become stable tokens such as <EMAIL_1>, restored when an agent writes them into a file. A session keeps its tokens in a private file. A prompt that carries a secret is refused. The operator can add names and patterns (below). Redaction is pattern-based: a short password, a key in a format nobody has seen and a name nobody listed go through.

The audit log

Every decision is a record in a log where each record is chained to the one before, so a change or a removal is named. The log grows by a day file per day and is not pruned yet.

docker compose exec worker warden policy          # what is in force, and the files it came from
docker compose exec worker warden status          # what it refused and redacted
docker compose exec worker warden audit verify    # the log has not been changed; exits 1 if it has

Your policy, and a repository's

deploy/config/warden.toml (created from warden.toml.example, every line commented) is your policy. It is a locked layer: a repository can add rules and protect more files in its own .warden/policy.toml, and can never loosen yours.

[[rules]]
id = "no-prod"
match = 'kubectl .*--context[= ]prod'
decision = "deny"
reason = "production is hands-off for agents"

[redact.pii]
names = ["Acme Corp"]
custom = [{ name = "customer_id", pattern = 'CUST-\d{6}' }]

Pin a policy with a corpus of expected decisions and check it: warden test corpus.toml.

Outside Shelf

Warden is its own component with its own binary and releases, and works without Shelf for Claude Code, Codex, Copilot and OpenCode (warden init --global --profile guarded, then warden doctor). Only Claude Code has been checked against the real agent, with a mock model. See the Warden README.

What it is not

Warden reads text. A program an agent writes and then runs can open any socket or read any file the worker can; Warden does not see inside it. A repository's checks run outside any agent hook. The container, the sandbox and the site allowlist stay the perimeter, and per-agent isolation is not built. Limits has the whole list.
